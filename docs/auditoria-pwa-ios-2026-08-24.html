01

Renderização React

O maior volume de re-renders evitáveis está em três pontos: as bolhas de mensagem, o heartbeat de presença, e os Providers de Auth/Theme no topo da árvore — este último afeta praticamente toda tela do dashboard, não só o inbox.

REACT-2

usePresence força o MessageThread inteiro a re-renderizar a cada 15s, mesmo sem atividade

Impacto Alto Risco baixo
95%
Evidência

src/hooks/use-presence.ts:20,148 — const RE_DERIVE_MS = 15_000 e setInterval(() => setNow(Date.now()), RE_DERIVE_MS). message-thread.tsx:214 desestrutura esse now direto do hook: const { getPresence, getRow, now } = usePresence();

// use-presence.ts
const tick = setInterval(() => setNow(Date.now()), RE_DERIVE_MS); // 15_000ms

// message-thread.tsx:214
const { getPresence, getRow, now } = usePresence();

Como now é state do hook e o componente o consome diretamente, MessageThread re-renderiza a cada 15s independente de qualquer mensagem nova — e combinado com REACT-1 e LIST-1, cada tick re-renderiza todas as mensagens visíveis.

Onde ocorre
src/hooks/use-presence.ts src/components/inbox/message-thread.tsx:214
Como validar

Correção
Baixo risco — não expor now no objeto padrão do hook, ou isolar quem realmente precisa dele atrás de um seletor separado.
Benefício
Remove um heartbeat de recomputação silencioso que hoje penaliza justamente as conversas longas — o cenário de uso mais comum e mais visado pelo usuário final.

Performance das listas

Este é o achado estrutural mais importante da auditoria: ele amplifica todos os outros achados de renderização (01) sempre que a conversa é longa.

LIST-1

Nenhuma virtualização — conversation-list e message-thread renderizam 100% dos itens no DOM

Impacto Crítico Risco médio-alto
85%
Evidência

package.json não tem nenhuma dependência de virtualização (react-window, react-virtual, @tanstack/react-virtual etc — confirmado por leitura completa do arquivo). message-thread.tsx:375-379 busca o histórico inteiro da conversa sem .limit()/.range(): .eq("conversation_id", conversationId).order("created_at", …). message-thread.tsx:1362/1372 — group.messages.map(...) renderiza cada mensagem como DOM real, incondicionalmente. conversation-list.tsx:668 — filtered.map(...) idem para a lista de conversas. 03

CSS e layout

A base de CSS já resolveu, de forma documentada e testada em dispositivo, a maior parte das armadilhas clássicas do WebKit iOS. Os achados abaixo são os pontos residuais.

CSS-2

backdrop-blur-sm embutido em MessageActions, montado (não desmontado) em toda mensagem

Impacto Alto Risco baixo
80%
Evidência
src/components/inbox/message-actions.tsx:157 — "...bg-popover/95 px-1 shadow-md backdrop-blur-sm transition-opacity...", aplicado à barra de ações (responder/reagir/encaminhar/apagar) de cada MessageBubble. Só opacity controla a visibilidade — o elemento nunca é desmontado — então cada mensagem carrega um backdrop-filter ativo no DOM o tempo todo. backdrop-filter é uma das propriedades mais caras para o compositor do WebKit em iOS, pois exige captura separada de tudo que está atrás do elemento.
Onde ocorre
src/components/inbox/message-actions.tsx:157
Como validar
Safari Web Inspector → Timelines → Rendering, abrir uma conversa longa e observar o tempo de composição/GPU; ou remover temporariamente backdrop-blur-sm numa build local e comparar.
Correção
Baixo risco — trocar por bg-popover sólido (sem blur) ou aplicar o blur só ao elemento ativo via montagem condicional em vez de opacity.
Benefício
Reduz pressão de GPU/memória que hoje escala linearmente com o tamanho da conversa — ganho direto combinado com LIST-1.

Animações

Não há biblioteca de animação no projeto — tudo é CSS nativo ou rAF manual, o que já remove uma classe inteira de risco. O único ponto onde uma propriedade cara é animada em sincronia direta com o toque é o Kanban.

ANIM-1

box-shadow animado junto com transform durante o drag de card no Kanban

Impacto Médio Risco baixo
70%
Evidência
Em src/components/pipelines/pipeline-board.tsx, o DragOverlay e o @keyframes deal-lift (próximo às linhas 420-439/517-529) animam transform (correto, só compositor) junto com box-shadow — de 0 1px 2px rgba(0,0,0,0.08) para 0 12px 24px -4px rgba(0,0,0,0.35). box-shadow não é propriedade de compositor no WebKit: é repintada a cada frame durante o gesto de arrastar em touch.
Onde ocorre
src/components/pipelines/pipeline-board.tsx (bloco @keyframes deal-lift)
Como validar
Arrastar um card no Kanban num iPhone real com Web Inspector → Timelines ligado; observar picos de "Layout"/"Paint" durante o drag.
Correção
Baixo risco — trocar a transição de box-shadow por duas camadas pré-renderizadas com cross-fade de opacity, ou remover a animação de sombra.
Benefício
Suaviza especificamente o momento de "pegar" o card no Kanban em touch — hoje é o único ponto do app com esse padrão.
✓ Já resolvido corretamente
  • Nenhuma ocorrência de Framer Motion (ou qualquer lib de animação) em todo o repositório — toda animação é CSS/keyframes nativo ou rAF manual.
  • .flip-modal-popup (transição de elemento compartilhado, globals.css:358-415) anima só transform/opacity, pré-promove com will-change antes de a animação começar (evita o soluço de promoção no primeiro frame), com escopo limitado à existência do popup.

  • will-change usado em apenas 2 lugares no repositório, ambos com escopo correto.
